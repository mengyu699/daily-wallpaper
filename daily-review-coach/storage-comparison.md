# 扣子平台三种存储方式详细对比（变量 vs 长期记忆 vs 数据库）

## 一、三种存储方式概述

### 1. 变量（Variables）
- **本质**：临时存储，会话级别的数据
- **持久性**：仅在当前会话有效，新会话重置
- **控制权**：开发者完全控制

### 2. 长期记忆（Long-term Memory）
- **本质**：AI自动总结的用户特征
- **持久性**：跨会话保存（理论上）
- **控制权**：扣子后端黑盒处理，开发者无法直接控制

### 3. 数据库（Database）
- **本质**：结构化持久存储
- **持久性**：永久保存
- **控制权**：开发者完全控制

## 二、具体使用方法

### 变量的使用方法

#### 1. 创建变量
```
设置路径：智能体设置 → 变量 → 添加变量
```

#### 2. 变量类型
- **系统变量**：user_id、conversation_id等
- **应用变量**：支持所有数据类型（String/Integer/Boolean等）
- **用户变量**：仅支持String类型，用于个性化服务

#### 3. 在提示词中使用
```markdown
# 提示词示例
你好{{user_name}}，今天的计划是{{today_plan}}
```

#### 4. 在工作流中使用
- 使用"变量赋值节点"写入值
- 在其他节点（如大模型节点）中读取变量值

### 长期记忆的使用方法

#### 1. 开启长期记忆
```
设置路径：智能体设置 → 记忆 → 长期记忆 → 开启
重要：必须勾选"支持在提示词中调用"
```

#### 2. 工作原理
- **自动记录**：AI自动识别并记录对话中的个性化信息
- **自动召回**：在回复时自动调用相关记忆

#### 3. 在工作流中使用
```yaml
长期记忆节点：
  输入：Query = "用户的工作规划"
  输出：outputList（相关记忆数组）
```

### 数据库的使用方法

#### 1. 创建数据表
```
设置路径：智能体设置 → 数据库 → 创建表
```

#### 2. 三种调用方式

**方式一：通过提示词+自然语言（最简单）**
```markdown
# 在提示词中配置
当用户说"保存规划：XXX"时，将XXX存入daily_plans表
当用户说"查询今日规划"时，从daily_plans表查询今日数据
```
用户直接对话即可：
- "保存规划：完成项目A、会议B、报告C"
- "我今天的规划是什么？"

**方式二：通过工作流节点（最稳定）**
```yaml
工作流：保存规划
  触发节点 → 数据库写入节点
    表名：daily_plans
    操作：INSERT
    数据：{user_id, date, plan_content}

工作流：查询规划
  触发节点 → 数据库查询节点
    表名：daily_plans
    条件：user_id = {{user_id}} AND date = TODAY()
```

**方式三：混合模式（推荐）**
- 提示词识别意图
- 触发对应工作流
- 工作流操作数据库

## 三、适用场景对比

### 变量适用场景
✅ **适合**：
- 单次会话内的临时数据
- 用户偏好设置（语言、主题等）
- 会话状态管理

❌ **不适合**：
- 需要跨会话保存的数据
- 早上规划晚上复盘（会话会断开）

### 长期记忆适用场景
✅ **适合**：
- 用户画像和偏好
- 习惯性行为记录
- 个性化推荐基础

⚠️ **问题**：
- 不透明，无法精确控制
- 可能有延迟或失效
- 无法保证100%召回

### 数据库适用场景
✅ **最适合**：
- 结构化数据存储
- 需要精确查询的数据
- 早上规划晚上复盘（强烈推荐）
- 历史记录追踪

## 四、针对"早上规划晚上复盘"的最佳方案

### 为什么数据库是最佳选择

| 对比项 | 变量 | 长期记忆 | 数据库 |
|-------|------|---------|--------|
| 跨会话保存 | ❌ | ⚠️ 不稳定 | ✅ |
| 精确查询 | ❌ | ❌ | ✅ |
| 可控性 | ✅ | ❌ | ✅ |
| 实时性 | ✅ | ⚠️ 可能延迟 | ✅ |
| 数据结构化 | ⚠️ | ❌ | ✅ |

### 具体实施方案

#### 步骤1：创建数据表
```sql
表名：daily_plans
字段：
- id (自增主键)
- user_id (用户标识)
- date (日期，格式：YYYY-MM-DD)
- morning_plan (早上规划)
- evening_review (晚上复盘)
- completion_rate (完成率)
- created_at (创建时间)
```

#### 步骤2：配置提示词
```markdown
## 场景识别与处理

### 早上规划场景
触发词：规划、计划、今天要做
操作步骤：
1. 识别用户输入的规划内容
2. 获取当前日期和用户ID
3. 调用数据库保存：INSERT INTO daily_plans...
4. 返回确认信息

### 晚上复盘场景
触发词：复盘、回顾、总结
操作步骤：
1. 获取当前日期和用户ID
2. 查询数据库：SELECT * FROM daily_plans WHERE...
3. 展示早上的规划
4. 引导用户进行复盘
5. 更新完成情况到数据库
```

#### 步骤3：创建工作流（可选但推荐）
```yaml
工作流1：morning_planning
  开始 → 接收输入 → 数据库写入 → 返回确认

工作流2：evening_review
  开始 → 数据库查询 → 展示规划 → 接收复盘 → 更新数据库
```

## 五、其他用户的实践经验

### 成功案例
1. **信息收集助手**：使用数据库存储用户提交的联系信息
2. **读书笔记Bot**：数据库存储书名和笔记，支持查询
3. **学习助手**：数据库记录学习进度，长期记忆存储学习偏好

### 踩坑经验
1. **长期记忆不可靠**：多位用户反馈即使开启也可能失效
2. **变量会重置**：新会话所有变量清零
3. **数据安全**：建议使用软删除，避免误删无法恢复

## 六、最终建议

### 对于你的复盘教练场景

**推荐方案：数据库 + 工作流**

理由：
1. **100%可靠**：数据永久保存，不会丢失
2. **精确查询**：可以按日期、用户精确查询
3. **完全可控**：你能看到并控制所有数据

**实施要点**：
1. 使用数据库存储规划和复盘数据
2. 通过自然语言触发数据库操作（最方便）
3. 可选：配置工作流增强稳定性
4. 备选：开启长期记忆作为辅助

### 快速测试方法
```
1. 创建daily_plans表
2. 在提示词添加数据库操作逻辑
3. 测试对话：
   早上："保存今日规划：A、B、C三项任务"
   晚上："查询我的今日规划"
4. 验证是否正确返回
```

**记住**：数据库是唯一能保证跨会话数据不丢失的方案！
